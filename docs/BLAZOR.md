# A Blazor frontend for PlatformPlatform

**The Blazor frontend is planned, not built.** Every statement about it here is in the future tense on purpose. Statements about PlatformPlatform as it exists today were verified against commit `1cfde11d3` on 2026-09-11 and say so where it matters. Two figures are marked as estimates rather than measurements, and those are precisely the two still to be settled.

This document is the honest case for the change, disadvantages included. If you are evaluating PlatformPlatform for its backend architecture, you can stop reading: the choice of frontend makes no difference to it.

## What is planned

The same PlatformPlatform core with a Blazor WebAssembly frontend instead of a React one.

Vertical slice architecture, DDD and CQRS, PostgreSQL, YARP and the cookie-to-JWT path all stay, and Bicep, Azure Container Apps and the developer CLI remain the delivery foundation. Pages, components, forms, tables and charts move to C# and Razor. The Node toolchain is intended to leave the frontend build path entirely.

The edition will be built on **.NET 11**, starting on RC1 and moving to general availability along the way. As a spin-off it is not bound by the React edition's SDK pin at 10.0.301. The divergence is worth taking because .NET 11 removes a Blazor constraint that .NET 10 carries, described under Content Security Policy below, and because a new codebase should not start a major version behind. .NET 11 is a standard-term support release rather than a long-term one, but its two-year window closes within weeks of .NET 10's three-year window, so the choice costs no meaningful runway.

FluentUI will be the component foundation rather than a reproduction of the existing design system. Functional parity is the goal. Visual parity is not.

This is an alternative, not a successor. PlatformPlatform classic remains the reference implementation, stays on React, and stays the place new backend capability lands first.

## Who it is for

Teams that are already all-C# and treat a second language in the stack as a cost rather than a feature. If your team debugs, tests and reviews in .NET all day, and the React half of a full-stack template is the half nobody wants to own, this edition removes that half rather than asking you to staff it.

If you have frontend people, or you want the deepest component ecosystem available, PlatformPlatform classic is the better choice and will stay ahead. This edition is not trying to win that comparison.

## Advantages

* **One language, one toolchain, one debugger** - The whole application will be C#. Step from a Razor event handler into a command handler in a single debugging session. One build, one formatter, one linter, one test runner, one dependency file, one set of upgrade decisions.
* **One shared application layer, whatever you build next** - Contracts, the typed API client, validation, localization and feature flag evaluation will live in one platform-neutral C# assembly that any .NET client consumes: the web application today, a desktop or mobile client later without rewriting any of it. With a TypeScript frontend, a native .NET client either reimplements that layer or wraps an API surface shaped for a different language, and the two drift.
* **The backend contract stops being copied** - Verified at `1cfde11d3`: 6,643 lines of generated TypeScript exist purely to mirror the OpenAPI documents, and four contract mirrors are maintained by hand, namely `build/environment.d.ts` at 206 lines mirroring `UserInfo.cs`, the `UnauthorizedReason` union in `AuthenticationMiddleware.ts`, `isValidReturnPath` mirroring `ReturnPathHelper`, and the feature flag manifest round trip from `FeatureFlags.cs` through a generated JSON file and a Node script into two generated TypeScript files. These become direct references to the same types, so a rename becomes a compile error rather than silent drift.
* **Server-side validation meets the native idiom** - PlatformPlatform already validates on the server and renders the result in the form. Verified at `1cfde11d3`, the React form binds `mutation.error?.errors` into a custom validation context. Blazor's `EditContext` and `ValidationMessageStore` express the same design without that custom context, so here the framework default is a closer fit than what the React version had to build.
* **The frontend toolchain churn is not inherited** - Verified at `1cfde11d3`, the classic build system carries a documented deferral of TypeScript 7 because the OpenAPI generator cannot load it, an exact pin on the Lingui SWC plugin because that plugin API is not semver-stable, a dedicated troubleshooting skill for when that plugin fails, and a deferred React Compiler adoption pending a bundler bump. None of these categories of problem exist in a Razor build.
* **Node leaves the repository entirely** - Once the five transactional email templates move from React Email to Razor components rendered with `HtmlRenderer`. That also removes three of the sixteen allocated development ports, the JavaScript app resource in the Aspire host, the development static proxy, the four `.esproj` shims, and roughly 1,500 lines of npm and Playwright plumbing in the developer CLI.
* **The micro-frontend split disappears rather than being reimplemented** - Verified at `1cfde11d3`, the classic frontend runs three separate bundles composed at runtime through module federation, with React, the router, the i18n catalog and the query client forced to singletons across the boundary so a single router can own history. The Blazor edition will be one application, so that whole category of configuration and its failure modes will not exist.
* **Feature flags are read, not regenerated** - The flag registry is already C#. The Blazor edition consumes it directly instead of emitting a manifest and generating a TypeScript union from it.
* **A shared .NET testing stack and isolated component testing** - Verified at `1cfde11d3`, the React frontend has no unit tests at all: roughly 53,600 lines of production code rest on 9,283 lines of end-to-end Playwright specifications as their only safety net, and no continuous integration workflow runs them, so they are a developer-machine gate. In the Blazor edition the shared application layer will be exercised by the same xUnit stack as the backend, and components will be testable in isolation, so a business rule can carry one test covering both the server that enforces it and the client that presents it.
* **One team can own the whole product** - A .NET team maintains the frontend without a second specialism, a second review culture or a second set of hiring criteria. For a business building line-of-business software rather than a consumer product, that is often the difference between a frontend that keeps pace and one that quietly rots because the person who understood it moved on.
* **A smaller dependency surface to audit** - Verified at `1cfde11d3`, the frontend declares 55 direct npm dependencies which resolve to 710 packages in the lock file, each an entry in the software bill of materials and a path for a supply-chain compromise. Assumption, not measured: the NuGet graph for an equivalent Blazor application will be an order of magnitude smaller and dominated by packages from a single vendor with a published security process. NuGet is not immune to the same class of attack, so the claim is deliberately narrow: fewer parties to trust, and fewer to review when something is disclosed.
* **A published support lifecycle for the whole stack, not half of it** - .NET states its support windows with dates, three years for long-term releases and two for standard-term ones, scheduled years ahead. React, the bundler, the router and the internationalization toolchain publish no equivalent commitment. For software a business expects to run for a decade, knowing when each piece stops receiving security fixes is itself a feature.

## Disadvantages

* **It starts behind, and it may stay behind** - Verified at `1cfde11d3`: 37 of the 76 non-merge commits in the preceding 90 days touched frontend code. PlatformPlatform classic is actively developed. This edition will not receive those improvements automatically, and every user-facing capability added upstream will need porting by hand. Adopt this only if you are comfortable with a frontend that tracks upstream late or not at all.
* **The component ecosystem is thinner** - The plan is to build on FluentUI rather than reproduce the classic design system, which is 84 components on Base UI and Tailwind 4 as verified at `1cfde11d3`. FluentUI will cover most of it, but not everything: one-time-password inputs, drag-and-drop upload, a command palette, date range picking, multi-select, resizable panels and Markdown rendering will have to be written or sourced, and FluentUI ships no charting components at all, so the dashboard will use a third-party Blazor chart library.
* **It will not look like PlatformPlatform classic** - The classic UI is a deliberately styled ShadCN-derived system with brand tokens and Apple Human Interface Guidelines control sizing. This edition will look like a FluentUI application. If the classic look is why you chose PlatformPlatform, this is the wrong edition.
* **The initial download is larger** - Estimated, not yet measured: a trimmed Blazor WebAssembly payload with a component library is expected in the low single-digit megabytes compressed, against a few hundred kilobytes for the React bundle. The intended mitigation is to server-render the public surface and start the WebAssembly runtime only after login, so the landing and signup pages do not pay the cost. This needs measuring before it is claimed as solved.
* **The Content Security Policy changes shape** - Verified at `1cfde11d3`, the classic policy is nonce-based with `strict-dynamic` and permits neither `unsafe-eval` nor `wasm-unsafe-eval`. This edition adds `'wasm-unsafe-eval'`, which permits WebAssembly compilation and instantiation and does not permit JavaScript `eval`. Because moving billing to Stripe's hosted pages also removes the Stripe host allowances from `script-src-elem`, `connect-src` and `frame-src`, and because dropping the Node development server removes a development-mode relaxation, the net policy is expected to be no weaker than today's. Building on .NET 11 removes the one remaining trap: on .NET 10 and earlier the `Virtualize` component emits dynamic inline style attributes on its spacer elements that a nonce-only `style-src` blocks, which silently breaks virtualization, and Microsoft documents `Virtualize` as CSP-compliant from .NET 11.
* **Localization is rebuilt on a different foundation** - Verified at `1cfde11d3`, classic carries 1,599 unique messages across two locales in Lingui ICU catalogs, merged at runtime across three layers. This edition will use the .NET localization stack. Two locales and simple plural rules make that a reasonable trade, but the catalogs do not transfer mechanically and the translated content will be rebuilt.
* **The AI rules corpus has to be rewritten** - This is the least visible cost and possibly the largest. A meaningful part of what PlatformPlatform provides is its rules and skills, refined over a year of daily use. The frontend half of that corpus encodes React, Lingui and bundler specifics and cannot be ported. Until an equivalent Blazor corpus exists, the multi-agent workflow will be less effective here than in classic.

## What stays the same

The self-contained system layout and domain architecture, the existing business behaviour, and the external identity integrations. The accepted multi-client foundation will add bootstrap and public-client authentication work below the API boundary. Hosting, build and deployment integration will need to accommodate the Blazor artifacts and the .NET 11 toolchain, and the intended reuse of Stripe webhook handling and billing reconciliation will be tested if billing is included.

If you are evaluating PlatformPlatform for its backend architecture, the two editions are the same product.
